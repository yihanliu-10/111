# 辩论模块设计

## 1. 定位

双头模型（意愿头 p_want + 风险头 p_risk）负责**出数**，Agent 链负责**做决策**。
两端职责清晰分离：

- 模型侧：可离线训练、可回测、可监控的分数与 SHAP 归因；
- 决策侧：可解释、可审计、政策可热改的裁决流程。

辩论模块只处理**灰区案件**——闸门无法直接批/拒的那部分。设计目标是：
在灰区把「批多少、批不批」的判断从单一 prompt 拆成对抗性的多视角论证，
再由裁判收敛，最后用纯代码校验兜底。

## 2. 状态机

```
S1 硬规则闸门(gate.py，纯代码)
 ├─ p_risk >= 硬拒绝线            → AUTO_REJECT（终态）
 ├─ p_risk<=快批线 且 p_want>=意愿线 → AUTO_APPROVE，按等级上限定档（终态）
 └─ 其余 → 灰区，进入辩论
S2 独立立论(agents.run_opening ×2)
 └─ 营销代理、风控代理各自只见案件包与政策，互相不可见 → Opening
S3 反驳轮(agents.run_rebuttal ×2，最多 1 轮)
 ├─ 若两份 Opening 处置与档位完全一致 → 已收敛，跳过
 └─ 否则各自针对对方 Opening 逐条回应 → Rebuttal（允许 concede 让步）
S4 裁判裁决(agents.run_judge)
 └─ 输入完整辩论记录，输出结构化 Verdict
S5 确定性校验(validator.py，纯代码)
 ├─ 通过 → 终态
 ├─ 违规 → 携违规项打回裁判重裁（仅一次）
 └─ 再违规 → MANUAL_REVIEW（终态）
S6 审计落盘(audit.py)
 └─ 案件包、闸门结论、全部立论/反驳/裁决尝试、校验轨迹 → audit/*.json
```

## 3. 角色设计

### 3.1 对称性原则

营销代理与风控代理的 system prompt **除立场段外逐字对称**（见 `prompts.py`
的 `_ADVOCATE_TEMPLATE`）。辩论质量的差异应来自立场与证据挖掘方向，
而不是某一方拿到了更长/更强的提示词。

### 3.2 共同约束

- 论据只能来自案件包（分数、SHAP、申请人信息）与当期政策，禁止编造；
- 每条论点必须落到具体证据（写明分数/特征取值/政策条款）；
- 硬约束对双方同等生效：硬拒绝线之上不得主张批准，建议档位不得越等级上限。

### 3.3 裁判

裁判不代表任何一方，只对证据质量与政策合规负责。裁决规则写死在 prompt：
硬线一律拒、越档必须降、证据不足转人工、理由必须可核对。
由于 claude-opus-5 不接受 temperature，裁判一致性靠 prompt 中
「相同输入应得出相同结论」的显式约束 + 同案多跑验收。

## 4. 结构化输出

三个 LLM 输出模型（`Opening` / `Rebuttal` / `Verdict`）直接作为
`client.messages.parse(output_format=...)` 的 schema，SDK 侧完成 JSON Schema
生成与解析校验，代码里拿到的是 Pydantic 实例——不存在手写 JSON 解析。

schema 设计约束（结构化输出的 API 限制）：

- 扁平结构，无递归；
- Optional 字段显式默认值；
- 枚举用 `Literal`（处置、档位、角色）。

## 5. 确定性校验（S5）

裁判是 LLM，会错；政策是硬的，不能错。`validator.py` 用纯代码复核：

| 检查项 | 规则 |
|---|---|
| 硬线 | APPROVE 时 p_risk 必须低于硬拒绝线 |
| 档位合法 | tier 必须在政策档位表内 |
| 等级上限 | tier 不得超过 p_risk 等级对应上限；不可批等级不得 APPROVE |
| 字段一致 | REJECT / MANUAL_REVIEW 时 tier 必须为空 |

打回策略：首次违规把违规项列表注入裁判 prompt 重裁一次；
第二次违规不再信任模型，直接 MANUAL_REVIEW。
这保证**无论模型输出什么，越线决策都到不了终态**。

## 6. 成本控制

- S1 纯代码：快批/硬拒案件零 LLM 成本（demo 数据里 4 案有 2 案在此终结）；
- S3 收敛跳过：立论一致的灰区案件省 2 次调用；
- 灰区上限：2 立论 + 2 反驳 + 最多 2 裁决 = 每案至多 6 次调用，常态 5 次。

## 7. 审计

每案落一个 JSON（`audit/{case_id}_{utc时间戳}.json`），字段：

- `case_packet`：进入决策时的完整案件包（含政策版本）；
- `gate`：闸门结论与理由；
- `openings` / `rebuttals`：双方全部发言（收敛跳过时 rebuttals 为 null）；
- `judge_attempts`：每次裁决尝试 + 对应校验违规项（含被打回的那次）；
- `final`：终态、档位、决策主体（gate / judge / validator_escalation）。

监管问「这笔为什么批」时，答案是一个文件，不是一段复述。

## 8. mock 模式

`--mock` 走 `agents.py` 的确定性分支，零网络调用：

- 覆盖全部状态迁移：快批、硬拒、反驳轮、收敛跳过、S5 打回-修正；
- mock 裁判首次**刻意越档一级**，用于演练校验打回闭环——这是特性不是 bug；
- 用于 CI / 本地开发验证状态机，不用于评估决策质量。

## 9. 二期规划

- **SHAP 归因摘要 Agent**：把 SHAP 表翻译成面向客户经理的中文解释；
- **复盘 Agent**：对辩论决策与纯闸门决策做 swap set 离线评估；
- **真模型接入**：`case_packet.py` 数据源换成双头 LightGBM 预测 + SHAP，
  下游（闸门/辩论/校验/审计）不需要改动。
